## Build D — Templated automation deployment (bundles + batch-apply)

A template-and-batch-apply layer on top of Build C. No new automation machinery; no changes to the queue, send-adapter, QA gate, runs tables, or `crm-generate-outreach`. Bundles just batch-create the same `project_automation_enrollments` rows the existing panel writes.

### 1. Schema — two new tables (one migration)

`automation_bundles`
- `id`, `name`, `description`, `tier` (nullable text), `project_type` (nullable text → matches `project_types.slug`/`venues.project_type`, null = any vertical), `sort_order int`, `is_active bool default true`, `created_at`, `updated_at`.

`automation_bundle_items`
- `id`, `bundle_id` (FK → bundles, on delete cascade), `automation_key text` constrained to `('followup_sequence','reactivation','review_request')`, `default_config jsonb default '{}'::jsonb`, `sort_order int`, timestamps.
- `UNIQUE (bundle_id, automation_key)`.

GRANTs + RLS (mirrors `pillar_templates` / `project_type_qualifier_config`):
- `GRANT SELECT` to `authenticated`, full DML to `service_role`.
- RLS: any authenticated user can `SELECT`; only `has_role(auth.uid(),'admin')` can `INSERT/UPDATE/DELETE`.
- `updated_at` trigger via existing `handle_updated_at()`.

Seed rows (idempotent inserts):
- "Tier 2 — Missed Money Recovery" → all three automations, manual_log adapter defaults matching Build C's `DEFS` (follow-up cadence `[0,1,3,7,14,30]`, reactivation manual_log, review_request `delay_hours: 2`).
- "Lead Catcher" → followup only.
- "Reviews Engine" → review_request only.
- "Reactivation" → reactivation only.

### 2. Batch-apply edge function — `apply-automation-bundle`

Input: `{ project_id: uuid, bundle_id: uuid, overwrite?: 'skip'|'replace' }` (default `skip`).

Flow:
1. JWT-validate caller; check `user_can_access_project(project_id)` via RPC; reject 403 otherwise.
2. Load `automation_bundle_items` for the bundle.
3. Load existing `project_automation_enrollments` for project (just `automation_key`).
4. For each item: if an enrollment already exists for that key → if `overwrite='skip'`, leave untouched (count as `skipped`); if `overwrite='replace'`, update `config` + `enabled=true`. Otherwise INSERT a new row with `enabled=true`, `config = item.default_config`.
5. Return `{ created: string[], skipped: string[], replaced: string[] }`.

Single source of truth: writes go to the exact same table Build C's panel writes. No new enrollment surface.

### 3. UI — apply bundle from the wizard / panel

New small component `ApplyBundleControl.tsx` placed at the top of `AutomationEnrollmentPanel.tsx` (one prop added; panel itself is otherwise unchanged):
- Select dropdown of active bundles, sorted by `sort_order`. Suggested bundles (matching project's `project_type` or `tier`) are surfaced first with a "Suggested" badge.
- "Apply bundle" button → calls edge function with default `skip`.
- If any keys would conflict, prompt: "X already has follow-up sequences configured — Keep existing / Replace with bundle defaults" (per-conflict isn't worth it, so a single radio applied to the whole apply call).
- On success, invalidate the enrollments query — the existing rows in the panel below repopulate; operator tweaks via the existing `EnrollmentRow`s. No parallel config surface.

Hook: `useAutomationBundles()` (list active bundles) + `useApplyBundle()` (mutation that calls the edge function and invalidates `useAutomationEnrollments` cache for that project).

No change to `VenueOnboardingWizard.tsx` — its automations step already renders `AutomationEnrollmentPanel`, so the new control appears there automatically.

### 4. Admin UI — `SettingsAutomationBundlesTab.tsx`

Mirrors `SettingsPillarsTab` pattern (list / add / edit / delete; admin-only). Per bundle: edit name/description/tier/project_type/sort_order/is_active; manage items (add/remove an `automation_key`, edit its `default_config` as JSON textarea, set `sort_order`). Wired into the existing admin `SettingsTab` tab list. Standard `useQuery`/`useMutation` against the two tables, no edge function needed for admin CRUD (RLS enforces admin-only writes).
